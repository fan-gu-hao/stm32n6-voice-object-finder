# Host-side source from dual-model development

[繁體中文](README.md) | [English](README.en.md)

This directory supplies the host-side implementations for vision generation and main-firmware migration, packaging alignment, fixed numerical comparisons, live-data collection, KWS generation, installation/builds, and deployment. The 33 scripts are complete Python or shell blocks from the original development conversation. They were originally pasted into a terminal, with here-documents for Python; filenames were assigned by purpose for publication and were not pre-existing filenames on the development computer.

These are stage-specific workflow snapshots that read historical models, frontend coefficients, directories, and version pointers. Some modify firmware source, switch diagnostic modes, build, or directly program the board; the table identifies those actions and their historical context. The final application is in [`firmware/`](../../firmware/); see the [build guide](../../docs/build.en.md) for its current build entry.

## Before and after the generation-output check

`generate_groupcv_model.py` preserves the original recursive artifact search. ST Edge AI completed generation, but the check stopped because identically named files appeared in both formal output and tool work directories. `inspect_groupcv_codegen.py` is the subsequent inspection restricted to formal `st_ai_output`; `install_build_groupcv.py` then uses those artifacts. The original check is retained as part of the actual development sequence.

## Publication adjustments and environment

The code bodies are retained, with device-specific identifiers replaced by environment lookups and `import os` added to Python only where needed:

| Environment variable | Use |
| --- | --- |
| `N6_SERIAL_PORT` | Serial device path opened by live comparison, collection, and voice-recording scripts |
| `N6_PROBE_SERIAL` | ST-LINK selection argument passed to STM32CubeProgrammer by flashing scripts |

The scripts retain `$HOME/STM32N6ai/course17_voice_object_finder`, historical tool-installation locations, and artifact pointers. Dependencies such as TensorFlow/NumPy and the original launcher interpreter are recorded in the source manifest. External artifacts, including reference models, frontend coefficients, and recordings, must match each stage.

The [source and hash manifest](source-provenance.json) records each conversation node and code-block location, SHA-256 hashes of the original block, extracted body, and public version, publication changes, and related outcomes. Publication checks only matched sources, parsed syntax, and checked identifier removal; no archived script, generation, training, or flashing was executed. See the [32-step source map](../../docs/development-source-map.json) for the complete stage mapping.
