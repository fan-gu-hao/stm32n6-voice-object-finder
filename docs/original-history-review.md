# 原始開發對話的工程證據覆核

[繁體中文](original-history-review.md) | [English](original-history-review.en.md)

本頁整理 2026-11-20 對原始開發對話及附件的覆核，補回從收音、訓練、移植、除錯到雙模型定版之間的實作與失敗經過。它與[工程流程](engineering-workflow.md)、[程式導覽](code-tour.md)及[結果](results.md)互補，不把最後成功的數字代替中間的工程工作。

## 覆核材料與證據層級

兩份原始對話各擷取 137 個輪次節點，其中 135 個共同繼承，合併為 139 個不同輪次；這不是 274 段互不重複內容，也不是把使用者與助手訊息分開計數。已覆核可取得的正文、程式碼、展開內容及八份使用者文字附件。

兩份來源壓縮包也已安全開啟並核對關鍵實作：視覺 ZIP 包含 2,041 個檔案，屬於另一視覺工程的早期快照，其模型雜湊開頭為 312ea458，與本雙模型工程的 331673 不同；另一份 RAR 包含 8,249 個項目、其中 7,722 個一般檔案，是 Runtime1100 上游手部框架。這些資料用來區分來源與版本，不把早期視覺工程的內容算成本案新增成果。核對關鍵實作不代表逐行讀過全部第三方程式庫。

歷史助手提供的 12 個不同名稱附件亦已取得並讀取，包含兩份整合 ZIP 與十份程式。九份獨立文字檔與對話內程式逐位元組相同；兩份 ZIP 及早期電腦收音程式補足原本未完整內嵌的內容。兩份 ZIP 自身均標示仍需編譯或上板核對，屬早期方案，不列為最後 KWS 找物版本的成功紀錄。所有附件僅供閱讀，覆核過程沒有執行其中的程式。

本頁使用的是對話中的終端回貼、當時列出的程式及下載的文字附件。**對話回貼不等於原電腦上的完整日誌檔**：有些指令回顯被截斷或混接，有些輪次沒有可見助手回答，部分內容只是待執行方案。下方短節錄保留實際數值並移除個人路徑、帳號及裝置識別資訊；它們不是完整原始日誌，也不能用來重新驗證未附的二進位資料。

判讀時分開四件事：

- **實際結果**：使用者貼出的工具輸出、板端紀錄或人工操作回報。
- **已保存實作**：當時列出的程式及公開來源能確認功能存在，但不單憑程式內的成功列印宣稱執行完成。
- **方案與修正指令**：說明打算如何做；須接到後續實際輸出，才能記為完成。
- **仍缺證據**：沒有輸出、附件內容尚未核對，或測試不足以支持更廣的結論。

公開頁面不包含私人對話全文、對話識別碼或登入資訊。既有可公開的原始產物與來源對應見[證據索引](evidence/development-history/README.md)。

## 啟動失敗：內容正確仍可能放錯位置

黑畫面診斷中讀到硬體錯誤例外狀態；返回位址解析落到斷言處理附近，但**沒有足夠證據把某個空指標、GPU2D 回呼或 KWS 初始化指定為唯一故障根因**。當時診斷指令另有兩個問題：執行指令跳到預設位址而非原地恢復，以及位址解析沒有抓到已列出的 PC／LR。這些工具問題不能與原本已存在的故障混為一談。

之後直接比較編譯後的原始程式與開機映像，取得以下實際結果節錄：

```text
原始程式在簽章映像中的偏移： 0x240
簽章映像內的程式內容完全一致： True

檢查通過：程式起始偏移為 0x400。
檢查通過：程式內容與原始編譯結果完全一致。
```

重新封裝補上 -align，保留原有 -nk、-of 0x80000000、-t ssbl、-hv 2.3。第一次替換又被唯讀檔案互動提示中斷，因此「封裝檢查通過」當下仍不等於重新燒錄完成；後續補完後才看到 KWS／FINDER 實際運行。

可確認的修正是**映像有效載荷從 0x240 改為 0x400，且核對完整內容未變**。此工程使用無金鑰標頭封裝；工具及檔名含 signed 不代表使用密碼學簽章。後續封裝流程保留向量、容量、區段及內容對齊檢查，並把應用與視覺命令區分開抽取。

## CPU／NPU 交接與兩層固定比較

早期 KWS 原始碼只處理 CPU 快取，而工作區啟用 NPU 快取。現行 [finder_kws.c](../firmware/Src/finder_kws.c)在 CPU 寫入新特徵之前，先依 64 位元組 NPU 快取列清理並失效，再使 CPU 舊副本失效及執行屏障；寫完後清理 CPU 快取，再啟動推論。兩模型在同一推論工作依序使用 NPU，各自保留模型上下文；此安排不是兩模型同時執行。

以下是 2026-10-07 對話回貼中的實際比較列，僅節錄結果：

```text
CMP,case=cup,path=INPUT,pc=cup,n6=cup,input_diff=0,input_max=0,output_max=0
CMP,case=bottle,path=INPUT,pc=bottle,n6=bottle,input_diff=0,input_max=0,output_max=0
CMP,case=phone,path=INPUT,pc=phone,n6=phone,input_diff=0,input_max=0,output_max=0
CMP,case=unknown,path=INPUT,pc=unknown,n6=unknown,input_diff=0,input_max=0,output_max=0
CMP,case=silence,path=INPUT,pc=silence,n6=silence,input_diff=0,input_max=0,output_max=1
CMP,case=cup,path=PCM,pc=cup,n6=cup,input_diff=0,input_max=0,output_max=0
CMP,case=bottle,path=PCM,pc=bottle,n6=bottle,input_diff=0,input_max=0,output_max=0
```

INPUT 直接使用電腦算好的量化特徵；PCM 多測板端前處理。兩路五類皆一致，PCM 路徑每段 637 個輸入值均相同；輸出差值以量化刻度計，靜音最多差一，其餘為零。這支持修正後這組資料的運算結果，**不能單獨證明早先所有誤辨都由快取造成**。電腦參考資料另見[固定參考 JSON](evidence/development-history/fixed_reference_20261007.json)。

## 從數值一致到現場可靠

早期實際程式已有分數 0.90、分差 0.25、連續兩窗及 1200 毫秒間隔，但音量只在接受判定後列印，畫面每窗都更新候選。以下低峰值接受列確實出現在回貼中：

```text
KWS,class=CUP,score=91,accept=1,peak=954,mfcc_ms=8,nn_ms=1
```

它證明該低振幅片段仍被接受；沒有當下發音標籤，不能單憑這行說使用者沒有講 cup。另一份有時間提示的測試則在「結束安靜」時段再次接受 PHONE，並漏接 cup／bottle，提供較明確的現場問題證據。

四段即時比較的結果如下；完整數值見[原始比較報告](evidence/development-history/live_comparison_20261007.json)。

| 實際提示 | 板端／電腦特徵輸入／電腦 PCM 重算 | INT8 輸入差異 | 輸出最大整數差 |
| --- | --- | --- | --- |
| 安靜 | phone／phone／phone | 0 | 0 |
| cup | cup／cup／cup | 0 | 0 |
| bottle | bottle／bottle／bottle | 0 | 3 |
| phone | phone／phone／phone | 0 | 1 |

瓶子雖排第一，板端分數約 41%，不足接受；安靜聲音三路都判成 phone。此輪安靜峰值 1748、三個詞皆超過 8800，因此接受規則第二版以 2500 作為起始音量門檻，接受後等待兩個安靜視窗，畫面只保留最後接受命令。這不是宣稱固定門檻適用所有環境。

診斷取樣也有版本差別：四段比較的安靜樣本刻意挑最像命令的視窗，三個語音挑最高能量視窗；後來 48 段收集改為各類皆依能量取樣，並在一般音量門檻之前進入收集路徑。不能把這兩組資料視為同一種隨機抽樣。

加入四段現場資料重訓後，自由輪流測試仍未見瓶子接受，且曾出現峰值 32767，因而加入逐窗五類分數、分差、命中數及滿刻度樣本統計。精確字串修改曾因排版不符而停止，之後改為唯一列印敘述定位；這是修改腳本的問題，不是另一個 NPU 故障。後續帶標籤的六次口令測試已包含這些詳細欄位，結果只接受兩次，該輪削波計數全為零。這些結果再推動 48 段資料收集與分組重訓。先前單次達滿刻度僅構成削波疑慮，尚未證明它造成漏接。

## 重訓、產物同步與最後結果

分組版本將原 142 訓練、49 驗證、4 段現場及新增 32 段合成 227 段開發池；原 49 段因此不再是最終獨立測試。相同 PCM 合併來源組別，拒絕標籤矛盾及開發／保留重複；每折的統計、噪音與量化校準只來自該折訓練資料。

訓練上限提高為 300 輪，80 輪後允許提早停止，耐心值 50；瓶子與安靜獲得較多增強及較高類別損失優先比例。五折最佳輪數為 82、28、66、9、79，最終採中位數 66。下載的原始訓練附件從第五折後段開始，保有完整 66 輪最終重訓與保留測試輸出；它不是五折每一輪的完整日誌。

[五折報告](evidence/kws-groupcv.json)的 224/227 與[保留報告](evidence/kws-int8-holdout.json)的 15/16 均與附件相符。保留測試唯一錯誤是 cup→phone；該窗 phone 分數約 60.9%，未達 90% 單窗接受門檻，不能直接描述成板子接受錯誤命令。

定版產碼曾已完成，後續遞迴搜尋卻把正式輸出與工具工作目錄的同名檔都算入，因而停止。修正限定正式輸出後確認產物；這是檔案檢查失敗，不是 Neural-ART 編譯失敗。安裝時同時更新模型、係數及量化參數：輸入零點從 8 改為 7，並關閉收集模式；沒有靠降低原接受門檻取得最後成功。

最後板上操作記錄為 cup、bottle、phone 各兩次接受，hello 與兩段安靜未接受。安靜階段沒有 KWS 推論列，支持音量閘控未誤觸發，不是模型將安靜分類正確的證據。短測試不提供跨說話者、跨環境或長期誤觸發率。

第三版中間訓練腳本、第五折與最終重訓、產碼、寫入及板測各自保留狀態：**不能用後來定版成功，倒推每個中間方案都曾完成執行。** 這次壓縮包覆核確認來源、版本及關鍵實作，沒有逐行讀完全部第三方程式。整合三物件展示、獨立供電與冷啟動結果，也不能由本頁節錄推定完成。展示影片仍待補。
